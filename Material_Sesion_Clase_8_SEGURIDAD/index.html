🔒 Seguridad básica en Spring Boot

La seguridad no es opcional. Es como ponerle candado a la puerta de tu casa: sin ella, cualquiera puede entrar y hacer lo que quiera con tu información.

Analogía clave: Tu app sin seguridad es como dejar la puerta abierta con un cartel que dice "pase, agarre lo que quiera". Agregar seguridad es poner cerradura, llave y portero.

Paso 1: Agregar la dependencia

En tu pom.xml, dentro de <dependencies>:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
⚠️ Al agregar esta dependencia, TODO se bloquea. Spring Security protege todas las rutas automáticamente. Verás un formulario de login que no existía antes. Usuario: user, contraseña: en la consola de arranque.

Paso 2: Configuración básica de seguridad

Crea la clase SecurityConfig.java:

package com.ejemplo.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web
    .builders.HttpSecurity;
import org.springframework.security.core.userdetails.*;
import org.springframework.security.crypto.bcrypt.*;
import org.springframework.security.crypto.password.*;
import org.springframework.security.provisioning.*;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filtro(HttpSecurity http)
            throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/css/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .formLogin(form -> form
                .loginPage("/login")
                .defaultSuccessUrl("/recursos", true)
                .permitAll()
            )
            .logout(logout -> logout
                .logoutSuccessUrl("/login?logout")
                .permitAll()
            );
        return http.build();
    }

    @Bean
    public UserDetailsService usuarios() {
        UserDetails usuario = User.builder()
            .username("docente")
            .password(encoder().encode("1234"))
            .roles("USER")
            .build();
        UserDetails admin = User.builder()
            .username("admin")
            .password(encoder().encode("admin123"))
            .roles("ADMIN", "USER")
            .build();
        return new InMemoryUserDetailsManager(usuario, admin);
    }

    @Bean
    public PasswordEncoder encoder() {
        return new BCryptPasswordEncoder();
    }
}

Paso 4: Controlador de login + botón logout

Agregar al controlador:

@GetMapping("/login")
public String login() {
    return "login";
}

En cualquier vista protegida, agregar botón de logout:

<form th:action="@{/logout}" method="post">
  <button class="btn btn-outline-danger">
    Cerrar sesión
  </button>
</form>
Resumen de roles:
  • docente / 1234 → puede ver y crear recursos
  • admin / admin123 → puede todo + sección admin
  • Sin login → solo ve la página principal

Mostrar/ocultar contenido según rol (Thymeleaf + Security)

Agregar al pom.xml:

<dependency>
    <groupId>org.thymeleaf.extras</groupId>
    <artifactId>thymeleaf-extras-springsecurity6</artifactId>
</dependency>

En tus vistas HTML:

<!-- Solo visible para ADMIN -->
<div sec:authorize="hasRole('ADMIN')">
  <a href="/admin/panel">Panel de administración</a>
</div>

<!-- Solo visible si está autenticado -->
<span sec:authorize="isAuthenticated()">
  Bienvenido, <span sec:authentication="name"></span>
</span>

<!-- Solo visible si NO está autenticado -->
<a sec:authorize="!isAuthenticated()" href="/login">
  Iniciar sesión
</a>

🧮 Getters y Setters con campos calculados

Un getter no solo devuelve un valor — puede calcular algo nuevo. Un setter no solo guarda — puede transformar antes de guardar. Esto es muy útil para campos derivados como totales, edades o estados.

Analogía: Un getter es como un cajero automático: no solo te da el dinero, puede calcular tu saldo actual. Un setter es como un filtro de agua: antes de guardar el agua, la limpia.

Ejemplo 1: Campo calculado con getter (no se guarda en BD)

Imaginemos una entidad Recurso con precio y cantidad. El total se calcula, no se almacena:

@Entity
public class Recurso {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nombre;
    private double precioUnitario;
    private int cantidad;

    // Getter calculado: NO tiene columna en la BD
    @Transient  // ← le dice a JPA: no guardes esto
    public double getTotal() {
        return precioUnitario * cantidad;
    }

    // Getters y setters normales...
    public double getPrecioUnitario() {
        return precioUnitario;
    }

    public void setPrecioUnitario(double precioUnitario) {
        this.precioUnitario = precioUnitario;
    }

    public int getCantidad() {
        return cantidad;
    }

    public void setCantidad(int cantidad) {
        this.cantidad = cantidad;
    }

    // ... más getters/setters
}
¿Por qué @Transient? Le dice a JPA: "este campo no existe en la base de datos, no lo guardes ni lo busques". Es un valor que se calcula al vuelo cada vez que lo pides.

Ejemplo 2: Setter que transforma antes de guardar

Un setter puede limpiar, formatear o validar el dato antes de almacenarlo:

@Entity
public class Beneficiario {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nombre;
    private String email;
    private String telefono;

    // Setter que transforma: nombre siempre en mayúsculas
    public void setNombre(String nombre) {
        this.nombre = (nombre != null)
            ? nombre.trim().toUpperCase()
            : null;
    }

    // Setter que limpia: teléfono solo dígitos
    public void setTelefono(String telefono) {
        if (telefono != null) {
            this.telefono = telefono
                .replaceAll("[^0-9]", "");
        } else {
            this.telefono = null;
        }
    }

    // Setter que valida: email siempre en minúsculas
    public void setEmail(String email) {
        this.email = (email != null)
            ? email.trim().toLowerCase()
            : null;
    }

    // Getters normales...
    public String getNombre() { return nombre; }
    public String getTelefono() { return telefono; }
    public String getEmail() { return email; }
}
Importante: El setter se ejecuta automáticamente cuando Spring recibe datos del formulario (@ModelAttribute). No necesitas llamarlo manualmente — el framework lo hace por ti.

Ejemplo 3: Getter calculado — Edad a partir de fecha

import java.time.LocalDate;
import java.time.Period;

@Entity
public class Beneficiario {
    // ... otros campos

    private LocalDate fechaNacimiento;

    // Getter calculado: edad en años
    @Transient
    public int getEdad() {
        if (fechaNacimiento == null) return 0;
        return Period.between(
            fechaNacimiento, LocalDate.now()
        ).getYears();
    }

    // En la vista Thymeleaf:
    // <td th:text="${beneficiario.edad}"></td>
}
En la vista: Thymeleaf accede a getEdad() automáticamente con ${beneficiario.edad}. No necesitas campo edad en la BD — siempre está actualizado.

Ejemplo 4: Getter que devuelve un estado textual

@Entity
public class Recurso {
    // ... otros campos

    private int cantidad;
    private boolean activo;

    // Getter calculado: estado legible
    @Transient
    public String getEstado() {
        if (!activo) return "Inactivo";
        if (cantidad == 0) return "Agotado";
        if (cantidad < 5) return "Bajo stock";
        return "Disponible";
    }

    // En la vista Thymeleaf:
    // <td th:text="${recurso.estado}"></td>
    //
    // Incluso con condicional de color:
    // <span th:text="${recurso.estado}"
    //   th:classappend="${recurso.estado == 'Agotado'}
    //     ? 'text-danger' : 'text-success'">
    // </span>
}
Pattern útil: En vez de guardar "Agotado" en la BD (que se desactualiza), lo calculas en tiempo real basándote en datos que sí están guardados (cantidad, activo).

🧪 QA: Calidad y Testing básico

QA (Quality Assurance) significa verificar que tu app funciona correctamente antes de que el usuario final la use. Es como revisar un examen antes de entregarlo.

Checklist de QA manual

Antes de cada deploy, verifica:

  1. ✅ La app arranca sin errores en localhost
  2. ✅ El login funciona (usuario correcto e incorrecto)
  3. ✅ Puedes crear un registro nuevo
  4. ✅ Puedes ver la lista de registros
  5. ✅ El campo calculado muestra valores correctos
  6. ✅ Un usuario sin rol ADMIN no ve la sección admin
  7. ✅ El logout funciona y redirige al login
  8. ✅ La app funciona en el celular (responsive)
Regla de oro: Si no lo probaste, no funciona. Nunca asumas que un cambio "pequeño" no rompe nada.

Flujo de QA antes de deploy

# 1. Compilar sin errores
$ ./mvnw clean package

# 2. Ejecutar en localhost
$ ./mvnw spring-boot:run

# 3. Probar manualmente:
→ Login correcto
→ Login incorrecto (muestra error)
→ Crear registro
→ Ver lista
→ Verificar campos calculados
→ Probar con rol diferente
→ Logout

# 4. Si todo funciona → commit + push
$ git add .
$ git commit -m "Agregar seguridad y campos calculados"
$ git push origin main
# → Render re-deploya automáticamente

Buenas prácticas de mantenimiento

  • Commits pequeños y descriptivos: un commit por funcionalidad.
  • No subir contraseñas reales: los usuarios en memoria son solo para demo. En producción real se usa BD.
  • Probar antes de pushear: siempre verificar en localhost primero.
  • Leer los logs: Render muestra todo en la pestaña Logs.
  • Un cambio a la vez: si algo se rompe, sabes exactamente qué fue.
Regla del redeploy seguro: Nunca hagas 5 cambios y un solo push. Haz 5 commits separados. Si algo falla, puedes hacer rollback al último commit bueno.

🔄 Redeploy: cambios en producción

Ya sabes deployar. Ahora aprenderás a hacer cambios en una app que ya está en internet — sin romperla.

Ciclo de redeploy seguro

  1. Cambiar código en tu editor local.
  2. Probar en localhost (QA manual).
  3. Commit con mensaje descriptivo.
  4. Push a GitHub.
  5. Render detecta y re-deploya automáticamente.
  6. Verificar en la URL pública.
La clave: Cada push es un deploy. Si el build falla, Render mantiene la versión anterior activa (zero-downtime deploy). Tu app nunca "se cae" por un build fallido.

Rollback en Render

Si un deploy nuevo rompe algo:

  1. Ir a tu servicio en Render → pestaña Events.
  2. Encontrar el deploy anterior que funcionaba.
  3. Click "Rollback to this deploy".
  4. Render restaura la versión anterior en segundos.
Nota: En el plan Free, solo puedes hacer rollback a los 2 deploys anteriores. Por eso es importante hacer commits pequeños y frecuentes.

Ejemplo: Agregar seguridad a un proyecto ya deployado

# 1. Ya tienes tu app en Render sin seguridad
# 2. Agregas Spring Security (pom.xml + SecurityConfig)
# 3. Pruebas en localhost
$ ./mvnw spring-boot:run
→ Verificas login, roles, logout

# 4. Commit descriptivo
$ git add .
$ git commit -m "Agregar autenticación con Spring Security (2 roles)"

# 5. Push → redeploy automático
$ git push origin main
→ Render detecta, Docker build, 3-8 min

# 6. Verificar en la URL pública
$ curl -I https://mi-app.onrender.com/login
HTTP/1.1 200 OK
