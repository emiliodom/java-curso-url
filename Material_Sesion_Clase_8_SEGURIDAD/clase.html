Sesión de Clase 8 — Seguridad, QA y Mantenimiento

Unidad 8: proteger la app con Spring Security, campos calculados, QA manual y redeploy seguro.
Abrir ejercicios
Comprensión de Spring Security

Objetivos (hoy)

  • Agregar autenticación con Spring Security (login, logout, roles).
  • Implementar getters calculados (@Transient) y setters con transformación.
  • Aplicar un checklist de QA manual antes de cualquier deploy.
  • Hacer un redeploy seguro con cambios de seguridad.
  • Mostrar/ocultar contenido en Thymeleaf según el rol.

Normas rápidas

  • No subas contraseñas reales (InMemory es para demo).
  • Siempre prueba en localhost antes de hacer push.
  • Commits pequeños: un commit por funcionalidad.
  • Si el login no funciona en localhost, no hagas deploy.

Caso sugerido

Continuar con el proyecto de la entidad sin fines de lucro (ya deployado en Semana 7).
  • Agregar Spring Security con 2 roles.
  • Agregar campo calculado (ej: total, edad o estado).
  • Agregar setter con transformación (ej: nombre en mayúsculas).
  • QA manual → commit → push → verificar en Render.

⚠️ Preparación previa

Pedir a los estudiantes antes de la clase:

  1. Verificar que su app sigue funcionando en Render (abrir la URL).
  2. Verificar que el proyecto corre en localhost sin errores.
  3. Tener Git configurado y poder hacer push.

Guión sugerido (120–150 min)

  • Pregunta detonadora: "Si tu app está en internet, ¿quién puede crear o borrar registros?"
  • Analogía: tu app sin seguridad es como una casa con la puerta abierta — cualquiera entra.
  • Mostrar el diagrama de autenticación en pantalla.
  • Meta del día: que tu app tenga login, roles, campos inteligentes, y que el redeploy sea seguro.

  1. Agregar spring-boot-starter-security al pom.xml en la demo.
  2. Ejecutar la app → mostrar que TODO se bloquea con un login automático.
  3. Crear SecurityConfig.java con: 
    @Configuration
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filtro(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/css/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .formLogin(form -> form
                .loginPage("/login")
                .defaultSuccessUrl("/recursos", true)
                .permitAll()
            )
            .logout(logout -> logout
                .logoutSuccessUrl("/login?logout")
                .permitAll()
            );
        return http.build();
    }

    @Bean
    public UserDetailsService usuarios() {
        UserDetails user = User.builder()
            .username("docente").password(encoder().encode("1234"))
            .roles("USER").build();
        UserDetails admin = User.builder()
            .username("admin").password(encoder().encode("admin123"))
            .roles("ADMIN", "USER").build();
        return new InMemoryUserDetailsManager(user, admin);
    }

    @Bean
    public PasswordEncoder encoder() {
        return new BCryptPasswordEncoder();
    }
}
  4. Crear login.html con formulario Thymeleaf.
  5. Probar: login correcto, login incorrecto, logout.
Punto clave para explicar
¿Por qué BCrypt? Nunca se guardan contraseñas en texto plano. BCrypt las "revuelve" (encripta). Ni siquiera tú puedes leerlas después.

¿Por qué InMemory? Para este curso es suficiente. En producción real se usa una tabla en la BD.

Mostrar los 4 patrones del material interactivo:

  1. Getter calculado con @Transient: getTotal() = precio × cantidad. No se guarda en BD.
  2. Setter con transformación: setNombre() → trim().toUpperCase(). Se guarda limpio.
  3. Getter de edad: getEdad() a partir de fechaNacimiento usando Period.between().
  4. Getter de estado: getEstado() que devuelve "Disponible", "Agotado", "Bajo stock".
Actividad del estudiante
Cada equipo elige 1 getter calculado y 1 setter con transformación para agregar a su entidad. Deben poder explicar POR QUÉ no guardan el campo calculado en la BD.
Error común
Poner @Transient en un campo que SÍ quieren guardar. Resultado: el dato desaparece al reiniciar. Enfatizar: @Transient = "no guardes esto".

Entregar el checklist de 8 puntos a cada equipo:

  1. La app arranca sin errores en localhost.
  2. Login funciona (correcto e incorrecto).
  3. Puedo crear un registro nuevo.
  4. Veo la lista de registros.
  5. El campo calculado muestra valores correctos.
  6. Un usuario sin rol ADMIN no ve la sección admin.
  7. Logout funciona y redirige al login.
  8. La app se ve bien en el celular.
Mensaje clave
"Si no lo probaste, no funciona." Este checklist es el equivalente a revisar un examen antes de entregarlo. Un profesional SIEMPRE verifica antes de publicar.

  1. Cada equipo hace git add . → commit → push con los cambios de seguridad.
  2. Abrir Render → verificar que el build arranca automáticamente.
  3. Mientras esperan el build (3-8 min), revisar la sección de errores comunes.
  4. Cuando esté Live → probar login en la URL pública.
  5. Probar desde el celular: ¿funciona el login? ¿Se ve bien?
Si el build falla
Render mantiene la versión anterior activa (zero-downtime). No es emergencia. Leer los logs → encontrar el error → corregir → push de nuevo.

Si hay tiempo, agregar thymeleaf-extras-springsecurity6 y usar sec:authorize:

  • Mostrar "Bienvenido, [nombre]" solo si está autenticado.
  • Mostrar un botón "Admin" solo si tiene rol ADMIN.
  • Hacer un segundo push → ver el redeploy.
Nivel avanzado (opcional)
Los equipos más avanzados pueden intentar agregar un tercer rol o proteger rutas específicas del CRUD (ej: solo ADMIN puede borrar).

Ticket de salida
Cada equipo comparte:
1. ¿Qué getter calculado agregaron y por qué?
2. ¿Qué setter con transformación implementaron?
3. ¿Qué fue lo más difícil de la seguridad?
4. Una frase: "La seguridad en una app es como ______ porque ______."
