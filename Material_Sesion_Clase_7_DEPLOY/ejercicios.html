Ejercicio 1 — Verificar localhost

Antes de publicar, tu app debe funcionar localmente.

  1. Abre tu terminal en la carpeta del proyecto.
  2. Ejecuta: ./mvnw spring-boot:run
  3. Abre http://localhost:8080 en el navegador.
  4. Verifica que puedas listar, crear y ver registros.
Si no funciona aquí, NO sigas
Resuelve los errores locales primero. Deploy no arregla bugs.

Ejercicio 2 — Crear Dockerfile

Render no tiene Java como runtime nativo (solo soporta Node.js, Python, Ruby, Go, Rust y Elixir). Necesitas un Dockerfile que le diga cómo compilar y ejecutar tu app.

  1. En la raíz del proyecto (junto a pom.xml), crea un archivo nuevo.
  2. Nombre: Dockerfile (sin extensión)
  3. Contenido:
# Etapa 1: Compilar el proyecto
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY . .
RUN ./mvnw clean package -DskipTests

# Etapa 2: Ejecutar la aplicación
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 10000
CMD ["java", "-Xmx256m", "-jar", "app.jar"]
¿Qué hace cada línea?
Etapa 1 (build): Usa una imagen con Maven y Java 17 para compilar tu proyecto. COPY . . copia tu código al contenedor. RUN ./mvnw clean package compila y genera el .jar.
Etapa 2 (run): Usa una imagen ligera solo con Java 17 JRE. Copia solo el .jar compilado. EXPOSE 10000 documenta el puerto. CMD ejecuta la app con límite de 256 MB de memoria.

Ejercicio 3 — Ajustar application.properties

Configura tu app para que funcione tanto local como en Render.

# Puerto dinámico (Render asigna su propio puerto)
server.port=${PORT:8080}

# Base de datos H2 en memoria (producción simple)
spring.datasource.url=jdbc:h2:mem:proddb
spring.datasource.driver-class-name=org.h2.Driver
spring.jpa.hibernate.ddl-auto=update
spring.jpa.database-platform=org.hibernate.dialect.H2Dialect

# Consola H2 (útil para verificar datos)
spring.h2.console.enabled=true
spring.h2.console.path=/h2-console
spring.h2.console.settings.web-allow-others=true
¿Qué significa ${PORT:8080}?
Lee la variable de entorno PORT. Si existe (en Render), la usa. Si no (en tu PC local), usa 8080 como respaldo. Es una configuración "dos en uno".

Ejercicio 4 — Verificar .gitignore

Asegúrate de NO subir archivos innecesarios. Crea también un .dockerignore con el mismo contenido.

# Tu .gitignore (y .dockerignore) debe incluir al menos:
target/
*.class
*.jar
*.log
.idea/
*.iml
.DS_Store
*.mv.db
*.trace.db
¿Por qué? La carpeta target/ contiene archivos compilados que Render genera él mismo. Subirlos desperdiciaría espacio y podría causar conflictos.

Ejercicio 7 — Crear Web Service

  1. New + → Web Service
  2. Build and deploy from a Git repository
  3. Conectar tu repositorio
  4. En Language, seleccionar Docker (no elegir Java — no existe como opción nativa)
  5. Configurar:
    • Name: (nombre de tu app)
    • Branch: main
    • Dockerfile Path: ./Dockerfile (se detecta automáticamente)
    • Plan: Free
  6. Nota: No hay campos de Build Command ni Start Command — el Dockerfile los reemplaza.

Ejercicio 8 — Verificar el build en los logs

El Dockerfile ya incluye -Xmx256m en el CMD, así que la memoria está limitada automáticamente. Ahora obsérvalo en acción.

  1. Después de crear el Web Service, ve a la pestaña "Logs".
  2. Observa cómo Render ejecuta docker build usando tu Dockerfile.
  3. Busca estas líneas clave:
    • Step X/Y : FROM maven:3.9-eclipse-temurin-17 → Descargando imagen base
    • BUILD SUCCESS → Maven compiló correctamente
    • Started Application in X seconds → la app arrancó
¿Y si quiero cambiar la memoria sin tocar el Dockerfile?
Puedes agregar una variable de entorno en Render: Key: JAVA_TOOL_OPTIONS, Value: -Xmx256m. Esto sobreescribe el valor del CMD.

Ejercicio 10 — Verificar URL pública + Re-deploy

Parte A: Verificar
  1. Cuando Render muestre ● Live, copia la URL.
  2. Abre la URL en tu navegador.
  3. Abre la URL en tu celular.
  4. Crea un registro nuevo desde el celular.
Parte B: Re-deploy
  1. Haz un cambio pequeño en tu código (ej: cambiar un título).
  2. Ejecuta: 
    git add .
git commit -m "Cambiar título para probar re-deploy"
git push origin main
  3. Abre Render → observa que el build arranca solo.
  4. Espera a que termine → verifica el cambio en la URL.
¡Lo lograste! Si el cambio se ve en la URL, dominas el ciclo completo de deploy.

🎁 Bonus — Evitar el "cold start" con cron-job.org

¿Sabías? El plan gratuito de Render apaga (spin down) tu app después de 15 minutos sin recibir tráfico entrante (inbound HTTP). Render monitorea las peticiones que llegan desde fuera a nivel de load-balancer — no la actividad interna del proceso. Un @Scheduled de Spring o un hilo background dentro de la app no cuenta como actividad y no evita el spin-down. La primera visita posterior tarda 30-60 segundos mientras la JVM arranca de nuevo.
⚠️ ¿Por qué no un cron interno? Si agregas @Scheduled(fixedRate=840000) en tu código Spring Boot, esa tarea se ejecuta dentro del mismo proceso. Render no ve eso como tráfico entrante — la app se dormirá igual. Necesitas un ping externo.
Workaround: Ping EXTERNO automático cada 14 minutos
  1. Ve a cron-job.org y crea una cuenta gratuita.
  2. Haz clic en "Create Cronjob".
  3. En URL, pega tu URL de Render: https://mi-app.onrender.com.
  4. En Execution schedule, elige "Every 14 minutes" (personalizado).
  5. Guarda el cron job.
  6. Verifica: espera 15+ minutos y abre tu app — debería cargar rápido (~2-5s en vez de ~60s).
Resultado: cron-job.org hará un GET a tu URL cada 14 min, impidiendo que Render apague el contenedor. Tu app responde rápido 24/7 sin costo.
