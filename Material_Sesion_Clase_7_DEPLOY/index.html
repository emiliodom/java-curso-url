¿Qué significa "deploy"?

Deploy = publicar. Es como imprimir un documento y ponerlo en un tablón público. Tu app pasa de funcionar solo en tu computadora a estar disponible para cualquier persona con internet.

Analogía clave: Tu computadora es como tu cuaderno personal. Render es el tablón de anuncios de la escuela: todos pueden ver lo que publicas ahí.

Requisitos antes de deployar

Antes de publicar, tu proyecto necesita cumplir ciertas condiciones. Es como preparar la maleta antes de un viaje.

✅ Checklist pre-deploy

  • Git inicializado — tu proyecto tiene un repositorio Git
  • Repositorio en GitHub — todo tu código está subido
  • La app corre en localhost — sin errores al arrancar
  • Cuenta en Render — gratuita con GitHub
  • Archivo system.properties — indica la versión de Java

📁 Archivos que Render necesita

📂 mi-proyecto/
├── pom.xml ← Render lo detecta automáticamente
├── system.properties ← Versión de Java
├── 📂 src/
│ └── 📂 main/
│ ├── 📂 java/ (tu código)
│ └── 📂 resources/
│ ├── application.properties
│ └── 📂 templates/
└── .gitignore

🔧 system.properties

Este archivo le dice a Render qué versión de Java usar. Créalo en la raíz del proyecto:

java.runtime.version=17
¡Importante! Sin este archivo, Render puede usar Java 8 y tu app no arrancará.

⚙️ application.properties (para deploy)

Ajustes mínimos para que funcione en Render:

# Puerto que Render asigna
server.port=${PORT:8080}

# H2 en memoria para producción simple
spring.datasource.url=jdbc:h2:mem:proddb
spring.datasource.driver-class-name=org.h2.Driver
spring.jpa.hibernate.ddl-auto=update
spring.jpa.database-platform=org.hibernate.dialect.H2Dialect

# H2 Console (desactivar en producción real)
spring.h2.console.enabled=true
spring.h2.console.path=/h2-console
spring.h2.console.settings.web-allow-others=true
¿Por qué ${PORT:8080}? Render asigna un puerto dinámico. Con esta línea, tu app usa el puerto de Render si existe, o 8080 si corres local.

Git: Commit y Push (la base del deploy)

Render lee tu código directamente de GitHub. Si no haces push, Render no ve los cambios. Es como enviar una carta: si no la echas al buzón, no llega.

Paso 1 — Verificar estado

# ¿Qué archivos cambiaron?
$ git status

On branch main
Changes not staged for commit:
modified: src/.../application.properties
Untracked files:
system.properties

Los archivos en rojo son nuevos. Los modificados necesitan agregarse.

Paso 2 — Agregar y hacer commit

# Agregar TODOS los cambios
$ git add .

# Crear el commit con mensaje descriptivo
$ git commit -m "Preparar proyecto para deploy en Render"

[main abc1234] Preparar proyecto para deploy en Render
3 files changed, 12 insertions(+)
Regla de oro: Cada commit debe tener un mensaje claro. "cambios" no sirve. "Agregar system.properties para Java 17" sí.

Paso 3 — Push a GitHub

# Enviar cambios a GitHub
$ git push origin main

Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
To github.com:tu-usuario/tu-proyecto.git
abc1234..def5678 main -> main

Flujo resumido

# Los 3 comandos esenciales del deploy
$ git add .
$ git commit -m "Descripción del cambio"
$ git push origin main

# ¡Listo! Render detecta el push automáticamente
Automatización: Cada vez que haces push, Render re-deploya tu app automáticamente. ¡No tienes que hacer nada más!

Configurar Render paso a paso

Render es como un "horno" donde metes tu código y sale una app en internet. Solo necesitas conectar tu GitHub y configurar unas pocas cosas.

1. Crear cuenta en Render

  1. Ir a render.com
  2. Click en "Get Started for Free"
  3. Seleccionar "Sign in with GitHub"
  4. Autorizar el acceso a tus repositorios
¿Por qué Render? Es gratuito, no pide tarjeta de crédito, y se conecta directo a GitHub. Ideal para proyectos educativos.

2. Crear un Web Service

  1. En el Dashboard, click "New +" → "Web Service"
  2. Seleccionar "Build and deploy from a Git repository"
  3. Conectar tu repositorio de GitHub
  4. Render detecta que es un proyecto Java/Maven

3. Configuración del servicio

CampoValor
Namemi-app-recursos (el nombre que quieras)
RegionOregon (US West) — el más cercano gratis
Branchmain
RuntimeJava (detectado automáticamente)
Build Command./mvnw clean install -DskipTests
Start Commandjava -jar target/*.jar
PlanFree
Build Command explicado:
  • ./mvnw — usa el Maven que viene con el proyecto
  • clean install — limpia y compila todo
  • -DskipTests — salta pruebas para ir más rápido
Start Command explicado:
  • java -jar target/*.jar — ejecuta el .jar generado
  • Es como hacer doble clic para abrir un programa

4. Variables de entorno

En la sección "Environment" de Render:

KeyValue
JAVA_TOOL_OPTIONS-Xmx256m
¿Por qué -Xmx256m? El plan gratuito de Render tiene memoria limitada (512 MB). Con esto le decimos a Java que no use más de 256 MB.

5. Deploy y URL pública

  1. Click "Create Web Service"
  2. Render empieza a construir (Build) — tarda 3-8 minutos
  3. Cuando el status sea ● Live → ¡tu app está en internet!
  4. Tu URL será: https://mi-app-recursos.onrender.com
¡Momento mágico! Copia la URL y ábrela en tu celular. Tu app funciona desde cualquier dispositivo con internet.

Errores comunes y cómo resolverlos

Deployar rara vez funciona al primer intento. Eso está bien. Cada error es una pista para aprender.

❌ Build failed: Java version

Error: java.lang.UnsupportedClassVersionError
class file has wrong version 61.0, should be 52.0
Solución: Crear system.properties con java.runtime.version=17 en la raíz del proyecto.

❌ Port binding error

Web server failed to start. Port 8080 already in use
Solución: Agregar server.port=${PORT:8080} en application.properties. Render asigna su propio puerto.

❌ Application crashed / OOM

Error R14 (Memory quota exceeded)
Process running memory is larger than limit
Solución: Agregar variable de entorno JAVA_TOOL_OPTIONS=-Xmx256m en Render.

❌ mvnw: Permission denied

bash: ./mvnw: Permission denied
Solución: Ejecutar en tu terminal local:
git update-index --chmod=+x mvnw
git commit -m "Fix mvnw permissions"
git push origin main

❌ H2 file lock error

Database may be already in use: "mi-base.mv.db"
Solución: Cambiar a H2 en memoria para producción:
spring.datasource.url=jdbc:h2:mem:proddb

❌ La app tarda en responder (cold start)

Tu app se "duerme" después de 15 min sin tráfico
(Plan gratuito de Render)
Primera visita tras dormir → 30-60 s de espera (JVM + Spring Boot)
Explicación: En el plan free, Render "apaga" (spin down) tu app si no recibe tráfico entrante (inbound) durante 15 minutos. Render monitorea las peticiones HTTP que llegan desde afuera a nivel de load-balancer — no la actividad interna del proceso. Esto significa que un @Scheduled de Spring o un hilo interno no cuenta como actividad y no impide el spin-down. La siguiente petición externa despierta el contenedor, pero el arranque de JVM + Spring Boot tarda entre 30 y 60 segundos.
Workaround — Cron EXTERNO cada 14 min: Un servicio gratuito como cron-job.org o UptimeRobot puede hacer un ping HTTP externo a tu URL cada 14 minutos para que Render nunca apague la app.
  1. Crea una cuenta gratuita en cron-job.org.
  2. Crea un nuevo cron job con tu URL de Render (ej. https://mi-app.onrender.com).
  3. Configura la ejecución cada 14 minutos.
  4. Guarda → el servicio hará GET a tu app, manteniéndola despierta 24/7.
