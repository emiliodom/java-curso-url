Sesión de Clase 7 — Despliegue en Render

Unidad 7: publicar la aplicación web en internet usando Render (gratuito).
Abrir ejercicios
Comprensión de Git (add, commit, push)
Archivos de configuración para deploy
Lectura de logs y troubleshooting

Objetivos (hoy)

  • Preparar el proyecto Spring Boot para producción.
  • Ejecutar el flujo completo de Git: add → commit → push.
  • Configurar un Web Service en Render paso a paso.
  • Verificar que la app funcione con una URL pública.
  • Diagnosticar errores comunes de deploy.

Normas rápidas

  • No deploy sin commit descriptivo ("cambios" no vale).
  • Primero que funcione en localhost, luego deploy.
  • Todo error de build se resuelve leyendo el log.
  • El plan FREE se duerme — eso es normal.

Caso sugerido

Continuar con el proyecto de la entidad sin fines de lucro.
  • Verificar que el CRUD funciona en localhost.
  • Crear system.properties.
  • Ajustar application.properties.
  • Deploy a Render → URL pública.

⚠️ Preparación previa

Pedir a los estudiantes antes de la clase:

  1. Crear cuenta en render.com con su GitHub.
  2. Verificar que su proyecto corre en localhost sin errores.
  3. Tener Git instalado y configurado.

Guión sugerido (120–150 min)

  • Pregunta detonadora: "Si tu computadora se apaga, ¿tu app desaparece?"
  • Analogía: tu PC es tu cuaderno. Deploy es fotocopiar y poner el trabajo en un tablón público.
  • Mostrar el mapa del deploy en pantalla.
  • Meta del día: que tu app tenga una URL pública que cualquiera pueda abrir.

  1. Verificar que la app corre en localhost:8080 sin errores.
  2. Crear system.properties en la raíz: 
    java.runtime.version=17
  3. Ajustar application.properties: 
    server.port=${PORT:8080}
spring.datasource.url=jdbc:h2:mem:proddb
spring.datasource.driver-class-name=org.h2.Driver
spring.jpa.hibernate.ddl-auto=update
spring.h2.console.enabled=true
spring.h2.console.settings.web-allow-others=true
Punto clave para explicar
${PORT:8080} es como decir: "usa el puerto que Render te dé; si no hay, usa 8080". Es la misma idea que un respaldo.

Hacer la demo en la terminal real frente al grupo:

  1. git status — ver qué cambió.
  2. git add . — agregar todo.
  3. git commit -m "Preparar proyecto para deploy en Render"
  4. git push origin main — enviar a GitHub.
Actividad del estudiante
Que cada equipo haga los mismos comandos en su terminal. Abrir la terminal simulada para los que no pueden ejecutar en vivo.
Errores comunes aquí
• "nothing to commit" → No hicieron git add .
• "failed to push" → No tienen el remoto configurado (hacer git remote -v)
• "permission denied" → Token de GitHub expirado o no configurado

Proyectar la pantalla y hacer la configuración en vivo:

  1. Abrir render.com → Dashboard.
  2. New + → Web Service.
  3. Seleccionar repositorio de GitHub.
  4. Configurar:
    • Name: nombre-de-tu-app
    • Branch: main
    • Build: ./mvnw clean install -DskipTests
    • Start: java -jar target/*.jar
    • Plan: Free
  5. Ir a Environment → agregar JAVA_TOOL_OPTIONS=-Xmx256m
  6. Click "Create Web Service"
  7. Esperar el build (3-8 min). Leer los logs juntos.
Momento de celebración
Cuando el status cambie a ● Live, pedir que abran la URL en su celular. Ese momento de "mi app funciona en mi teléfono" es poderoso pedagógicamente.

  • Cada equipo replica el proceso con su propio proyecto.
  • Usar el cheatsheet como referencia rápida.
  • Si el build falla: revisar la sección de errores antes de llamar al docente.
  • Registrar la URL pública en el entregable.
No hacer por ellos
Si un equipo tiene un error, primero que lean el log. Preguntar: "¿Qué dice el mensaje?" antes de intervenir. El objetivo es que aprendan a diagnosticar.

Hacer un cambio pequeño para demostrar el ciclo completo:

  1. Cambiar un texto en una vista (lista.html o similar).
  2. git add . → commit → push
  3. Abrir Render → ver que el build arranca automáticamente.
  4. Esperar a que termine → verificar el cambio en la URL pública.
Mensaje clave
"Cada push es un deploy. Así funciona el desarrollo web real. Cambias → subes → se actualiza."

Ticket de salida
Cada equipo comparte:
1. Su URL pública.
2. Un error que tuvieron y cómo lo resolvieron.
3. Una frase: "Deployar es como ______ porque ______."
⏰ Importante: Cold start (plan free)
Render apaga la app tras 15 min sin tráfico entrante (inbound HTTP). Render mide solo peticiones externas a nivel de load-balancer, no la actividad interna del proceso. La primera petición posterior tarda 30-60 s. Explique que no es un error.

Pregunta frecuente de alumnos: "¿Y si pongo un @Scheduled en Spring?" → No funciona, porque Render no lo detecta como tráfico entrante. El ping debe venir de afuera.

Workaround gratuito: Crear un cron externo en cron-job.org que haga ping HTTP cada 14 minutos a la URL de Render → la app nunca se duerme.
Si hay tiempo, pida a un equipo que lo configure en vivo como demo.
