Sesion de Clase 6 — Persistencia, Login y Roles

Unidad 6: Login funcional + renderizado condicional + consultas y graficos.
Abrir ejercicios
Comprension de seguridad

Objetivos (hoy)

  • Implementar login con Spring Security.
  • Crear usuarios en memoria con roles (ADMIN, USER).
  • Mostrar/ocultar elementos segun el rol.
  • Buscar y filtrar datos con metodos del repositorio.
  • Mostrar un grafico con datos reales de la BD.

Normas rapidas

  • Primero el login funcional, luego estilo.
  • Si falla seguridad, revisar orden de reglas.
  • Las contrasenas SIEMPRE van cifradas.
  • Los campos del form de login se llaman username y password.

Caso recomendado

Continuar con "Recursos didacticos" de Semana 5.
  • Agregar login y roles al CRUD existente.
  • ADMIN: CRUD completo + estadisticas.
  • USER: listar + crear.
  • Filtro por tipo y busqueda por titulo.

Errores mas frecuentes

  • 403 Forbidden: el usuario tiene login pero no el rol necesario.
  • Login loop: olvidar .permitAll() en la ruta /login.
  • sec:authorize no funciona: falta la dependencia thymeleaf-extras-springsecurity6 o el namespace.
  • Grafico vacio: el controlador no envia los conteos al modelo.

Guion sugerido (120-150 min)

  • Pregunta guia: "Si cualquier persona puede ver los datos de los ninos del dispensario, ¿que problema hay?"
  • Lluvia de ideas: ¿por que necesitamos login?
  • Ejemplo cotidiano: el banco te pide contrasena para ver tu saldo.
  • Meta del dia: agregar un sistema de login funcional.
Consejo docente: conectar con el proyecto real del grupo. Los datos de beneficiarios son sensibles.

  • Mostrar las 2 nuevas dependencias en pom.xml (Security + Thymeleaf extras).
  • Preguntar: "¿que pasa si ejecuto la app solo con Security y sin configurar nada?" (Spring genera una contrasena aleatoria en el log).
  • Demostrar: agregar la dependencia, correr y ver la pantalla de login por defecto.
Momento aha: con solo agregar la dependencia, Spring bloquea TODO. Hay que configurar que es publico.

  1. Crear SeguridadConfig.java en carpeta configuracion/.
  2. Definir reglas: / y /css/** publicos, el resto requiere login.
  3. Definir usuarios: admin (ADMIN) y docente (USER) en memoria.
  4. Crear LoginControlador.java con ruta GET /login.
  5. Crear templates/login.html con formulario.
  6. Probar: admin entra, docente entra, credencial incorrecta muestra error.
Evidencia esperada: login funcional + redireccion a /recursos al iniciar sesion.

  1. Agregar namespace sec: al HTML.
  2. Mostrar nombre del usuario con sec:authentication="name".
  3. Ocultar boton "Borrar" para USER con sec:authorize="hasRole('ADMIN')".
  4. Agregar enlace a "Estadisticas" visible solo para ADMIN.
  5. Agregar boton "Cerrar sesion" con formulario POST a /logout.

Haz la simulacion interactiva del material HTML en pantalla grande para que todos vean.

  1. Agregar metodos al repositorio: findByTipo, findByTituloContainingIgnoreCase.
  2. Modificar controlador para aceptar @RequestParam opcional.
  3. Agregar formulario de busqueda en la vista.
  4. Probar: filtrar por "Video", buscar "java".
  5. Abrir consola H2 y ejecutar SELECT * FROM RECURSOS_DIDACTICOS.
Pregunta de reflexion: "¿por que conviene no escribir SQL directamente sino usar nombres de metodos?"

  1. Agregar countByTipo al repositorio.
  2. Crear ruta GET /recursos/estadisticas en el controlador.
  3. Crear vista estadisticas.html con Chart.js.
  4. Probar con datos reales: agregar 5+ recursos de distintos tipos.
  5. Mostrar grafico de barras y de dona lado a lado.
Impacto visual: cuando el grafico aparece con datos reales, el grupo entiende por que la BD es importante.

  • Reflexion: "¿Como explicarias a un companero por que es importante el login?"
  • Analogia: escribir 1 analogia para "rol" y 1 analogia para "consulta personalizada".
  • Adelanto Semana 7: despliegue (deploy) — llevar la app a internet.
  • Ticket de salida: escribir 3 pasos para agregar un nuevo rol al sistema.
